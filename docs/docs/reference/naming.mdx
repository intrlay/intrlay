# Generated names

Intrlay applies target-language naming conventions by default. Use a generation
options file to change conventions for a whole module, or an annotation to rename
one declaration. Neither changes the encoded layout.

## Defaults

For the tutorial's `selected_point` field:

| Target | Native field / view accessor |
| --- | --- |
| Rust | `selected_point` / `selected_point()` |
| C++ | `selected_point` / `selected_point()` |
| TypeScript | `selectedPoint` |
| C# | `SelectedPoint` |
| Python | `selected_point` |
| Dart | `selectedPoint` |

Type names normally use `PascalCase`. Generated operation names follow the same
language's style: `create_in_place`, `createInPlace`, or `CreateInPlace`.

## Type families

For a record named `Drawing`, the default API names identify the role of each
type:

| Target | Encoding input | Encoded view |
| --- | --- | --- |
| Rust | Owned `Drawing` or generic `DrawingInput` | `DrawingView`, parameterized by its storage |
| C++ | `DrawingInput<>`, with field source types selectable by template deduction | `DrawingView` and `DrawingViewReadOnly` |
| C# | `DrawingInput`; eligible records also have `DrawingSpanInput` | `DrawingView`, `DrawingViewReadOnly`, `DrawingSpanView`, and `DrawingSpanViewReadOnly` |
| TypeScript | Structural `DrawingInput` | `DrawingView` |
| Python | `DrawingInput` with `TypedDict` fields | `DrawingView` |
| Dart | `DrawingInput` class | `DrawingView` |

Rust derives add input and view types alongside the schema declaration. Rust
target generation emits a schema declaration with that derive, so the same
type family is available there. C++ schema declarations remain application
types; the generated module provides its own inputs and views, and its encoder
also accepts matching source declarations. The other targets use their input
types for construction without a separate `Drawing` value type.

TypeScript, Python, and Dart omit unused record and payload-enum input types.
Their presence follows construction and mutation dependencies, rather than
`create` alone; see [Accessor generation](annotations.mdx#accessor-generation-and-construction).

The suffixes describe representation, not ownership guarantees. A C++ input can
own a vector or borrow a span; a Rust input can borrow fields independently.
A C# `SpanInput` is a scoped `ref struct` for supported records. See
[Values, buffers, and views](../concepts/buffers-and-views.mdx) for the relationship
between these types and their storage.

### Enum names

Payload-free enums retain their original name, such as `Mode` or `DeviceKind`,
in C++, C#, TypeScript, Python, and Dart.
By default, fields and collection elements return this enum value directly; construction
accepts the same type. These declarations remain available when only readers
are generated.

A standalone `ModeView` is generated when `Mode` is explicitly exported.
Referenced enums need no wrapper just to read a field. C++, TypeScript, Python,
and Dart expose an export alias such as `DisplayMode` as `DisplayMode` and
`DisplayModeView`. C# aliases provide another view name while retaining the
same enum value type.

`Input` denotes a separate construction representation. A plain enum already
has the same value representation for input and reads, so it needs no suffix.
`Kind` names a separate discriminant only for an enum with payloads.

An explicit numeric projection uses packed tag arrays for inputs and views while
retaining the same enum declaration and export aliases for named constants.

Rust output retains the schema's `Mode` declaration. Its derive supplies
`ModeInput` as an alias and `ModeView` as part of the local Rust API, independently
of the exported roots.

For an enum with payloads, such as `DrawingCommand`:

- TypeScript uses a `DrawingCommandInput` union and numeric
  `DrawingCommandKind` discriminants. Python uses the same naming pattern, with
  `TypedDict` alternatives such as `DrawingCommandDrawPointInput` and an
  `IntEnum` for the kind.
- Dart uses a sealed `DrawingCommandInput` base with subclasses such as
  `DrawingCommandDrawPointInput`.
- C# provides `DrawingCommandInput.FromDrawPoint(...)` factories. Payload structs
  use names such as `DrawingCommandDrawPointInput`.
- C++ inputs for a Rust enum use payload types such as
  `DrawingCommandDrawPointInput<>`. A C++ `std::variant` schema retains its named
  payload types instead, such as `DrawPointInput<>`.
- Rust uses `DrawingCommandInput` variants for construction and
  `DrawingCommandVariantView` for matching borrowed payloads.

All targets expose `DrawingCommandView` for encoded access. See
[Enum tags](annotations.mdx#enum-tags) for tag values and payload access.

Generated companion names use the exported base name. Renaming `Drawing` to
`Sketch` produces `SketchInput` and `SketchView`; the same rule applies to other
companions. A schema declaration named `DrawingInput` would collide with the
input generated for `Drawing` in Rust, where both schema and input declarations
occupy the same module. Each target checks the names it emits in their actual
scopes and reports collisions rather than silently adjusting them.

## Configure a whole generation unit

Save this as `naming.json`. It keeps type and variant names in PascalCase, uses
snake_case for public view properties, and PascalCase for public static methods:

```json title="naming.json"
{
  "module_name": "drawing",
  "naming": {
    "fallback": { "case": "camelCase" },
    "rules": [
      {
        "selector": { "kind": "type" },
        "style": { "case": "PascalCase" }
      },
      {
        "selector": { "kind": "variant" },
        "style": { "case": "PascalCase" }
      },
      {
        "selector": { "kind": "property", "visibility": "public" },
        "style": { "case": "snake_case" }
      },
      {
        "selector": {
          "kind": "method",
          "visibility": "public",
          "require": ["static"]
        },
        "style": { "case": "PascalCase" }
      },
      {
        "selector": { "kind": "field", "visibility": "private" },
        "style": { "case": "camelCase", "prefix": "_" }
      }
    ]
  }
}
```

Apply it to the [tutorial schema](../tutorial.mdx#1-define-the-message):

```sh
intrlay generate --manifest-path protocol/Cargo.toml --language typescript --options naming.json --output generated/drawing.ts
```

The resulting API changes are:

| Default TypeScript | With this policy |
| --- | --- |
| `DrawingView.create(value)` | `DrawingView.Create(value)` |
| `DrawingView.createInPlace(bytes, value)` | `DrawingView.CreateInPlace(bytes, value)` |
| `view.selectedPoint` | `view.selected_point` |
| Input field `value.selectedPoint` | Still `value.selectedPoint`: it is a field, not a view property. |

Each rule replaces the complete style for matching symbols. **The last matching
rule wins**; `fallback` handles symbols that match no rule. Supplying `naming`
replaces the default policy rather than appending to it. When using the Rust
generation API, `NamingPolicy::for_language` supplies defaults that you can extend
before passing the policy to the generator.

## Rule fields

All selector conditions must match. Omitted conditions match any value.

| Selector | Accepted values / meaning |
| --- | --- |
| `kind` | `type`, `field`, `property`, `method`, `function`, `variant`, `parameter`, `local` |
| `visibility` | `public`, `protected`, `internal`, `private` |
| `require` | Every listed modifier must be present. |
| `exclude` | None of the listed modifiers may be present. |

Modifiers are `static`, `readonly`, `const`, `async`, `abstract`, `virtual`,
`override`, and `final`. A `const` symbol also matches `readonly`. Selectors
describe generated symbols; a target that does not emit such a symbol has
nothing for that rule to change. Parameters and local variables have no member
visibility.

`style.case` accepts `preserve`, `snake_case`, `camelCase`, `PascalCase`, or
`SCREAMING_SNAKE_CASE`. Optional `prefix` and `suffix` strings are applied after
casing. There are no user-supplied conversion callbacks.

`property` includes buffer accessors even when a target spells them as methods,
such as C++'s `selected_point()`. `method` covers operations such as construction
and replacement. The shared runtime package's own API names remain unchanged.

For property naming, `readonly` means that the property has no assignment setter.
A separate mutation method does not change this modifier. For example, a C#
getter with a `SetValue(...)` method still matches `readonly`; a TypeScript
getter/setter pair does not. This describes the generated member, not whether
its backing buffer can be modified.

## Rename one declaration

An explicit name for a direct declaration bypasses the policy, including its
affixes:

```rust title="Rust"
#[derive(intrlay::Intrlay)]
struct Reading {
    #[intrlay(typescript(name = "amount"))]
    sample_value: f32,
}
```

```cpp title="C++"
#include <intrlay/annotations.hpp>

struct INTRLAY() Reading {
    float sample_value INTRLAY(typescript.name = "amount");
};
```

TypeScript receives `amount`, while the source-language field remains
`sample_value`. Other targets keep their default names. A common `name = "..."`
applies to all targets unless overridden for one target; choose a literal spelling
valid in each affected language.

Enum payload accessors and flattened fields combine several name segments.
Explicit names replace their corresponding segments, then the property policy
applies to the complete path. For example, a variant named `Delivered` with a
field named `Ticket` produces `deliveredTicket` under the default TypeScript
policy, or `read_delivered_ticket` under a snake_case property policy with the
`read_` prefix. Input field and enum-constant naming policies do not supply
prefixes to that accessor path. Derived operation names, such as setter methods,
follow their own naming rules.

Invalid identifiers and collisions are errors. The generator does not silently
rename colliding declarations. See [Schema annotations](annotations.mdx#target-options-and-names)
for declaration scopes and target overrides.

## Modules and namespaces

`module_name` identifies the generation unit. `--module-name` overrides it from
the command line. C++ derives `intrlay_generated::<snake_case_name>` and C#
derives `IntrlayGenerated.<PascalCaseName>`; other targets use their file/module
system. The default module name is `Schema`.

Use `cpp.namespace` or `csharp.namespace` for an explicit namespace, independently
of symbol casing:

```json
{
  "module_name": "drawing",
  "cpp": { "namespace": "app::drawing" },
  "csharp": { "namespace": "App.Drawing" }
}
```

Namespace segments must be ASCII identifiers. Their literal spelling is preserved.
Namespaces do not deduplicate types across separately generated files.
